# /maintenance — ERP 긴급 보안 점검

## 2026-10-23 · 기능 추가 · 예약 점검 공지와 자동 재개

- 기존 공개 사이트와 ERP 페이지를 보존하고, 비인가 접근 대응을 묘사하는 공식 비상점검 공지를 별도 화면으로 추가했다. 점검 일정·대상 범위·진행 업무·남은 시간과 접속 재확인 및 공개 아카이브 링크를 제공한다.
- 확정 일정은 한국시간 2026-10-25 20:00부터 2026-10-26 12:00까지다. 활성 구간에만 공지가 열리며 종료 뒤 서버 상태를 재확인한 후 기존 ERP로 이동한다. 조회 실패는 서비스 재개로 처리하지 않는다.
- `/maintenance/preview`는 개발 환경 전용이며 확정 일정의 시작 5분 뒤 상태를 표현한다. 실제 차단을 켜지 않고 검토할 수 있으며 운영 빌드에서는 404다.
- 검증: `pnpm typecheck`, `pnpm lint`, `pnpm build`, 일정·proxy 테스트 9건, 기존 게스트·로컬 접근 회귀 테스트 17건, 독립 lifecycle 실행 21건 통과. 느린 navigation 중 중복 이동을 방지하고 30초 마운트 유지·focus·visibility 재진입에서도 이동 1회를 확인했다.
- 화면 검수: 로컬 개발 브라우저의 실측 320×844·390×844·520×900·521×900·1440×1000에서 공지의 제목·일정·버튼·푸터를 직접 확인했고 가로 넘침이 없었다. 최종 공지 브라우저 콘솔 오류·경고 0건. 데스크톱·모바일 전체 캡처를 저장했다.
- 실제 동작: 짧은 시험 일정에서 게스트 인증으로 열어 둔 `/erp` → `/maintenance` → `/erp`의 자동 전환을 관찰했다. 로컬 production 서버에서도 공지 200, 미리보기 404와 ERP 차단을 확인했다. 시험 환경변수는 제거하고 확정 일정의 `scheduled` 상태로 복원했다.
- 운영 경계: 로컬 구현·검증만 수행했다. 운영 배포, 운영 일정 활성화, 업무 데이터 mutation은 수행하지 않았다.
- 관련 커밋: `d08f9c69`

## 2026-10-23 · UI 개선 · 긴급 보안 봉쇄 안내 강화

- 첫 시안에 대한 추가 요청을 반영해 제목을 ‘내부 업무망 긴급 봉쇄’로 강화하고, 비인가 접근 감지·업무 기능 중지·접속 경로 격리를 명확히 안내한다.
- 적색 경보 띠, 접근 차단 표식, 보안 대응 현황, 점검 일정과 큰 재개 카운트다운을 기관 공지 형식으로 구성했다. 모바일에서는 차단 표식과 현황을 세로 배치한다.
- 일정·상태 조회·카운트다운 계산·자동 복귀 및 정리 로직은 기존 구현과 동일하다. 이번 변경은 공지 JSX와 CSS에 한정되며 운영 배포는 수행하지 않았다.
- 검증: `pnpm typecheck`, `pnpm lint`, `git diff --check` 통과. 독립 읽기 전용 리뷰에서 조치할 결함이 없었고, HEAD 대비 props·타이머·effect가 동일함을 비교했다. 앞선 예약 차단·자동 재개 실행 검증은 해당 코드가 변경되지 않아 재사용했다.
- 화면 검수: 실제 로컬 브라우저에서 320×844·390×844·560×900·561×900·760×900·761×900·1440×1000과 기본 패널 662×912를 직접 확인했다. 제목·차단 표식·일정·카운트다운·대응 현황의 겹침이나 잘림 및 가로 넘침이 없었다. 두 링크의 키보드 포커스 표시, 카운트다운 갱신을 확인했고 브라우저 오류·경고는 0건이었다.
- 최종 데스크톱·모바일 캡처는 로컬 산출물 `maintenance-desktop-urgent.jpg`, `maintenance-mobile-urgent.jpg`로 저장했다. 운영 활성 화면과 재개 경계는 이번 UI 변경 후 별도로 재실행하지 않았다.
- 관련 커밋: `5c24d435`

## 2026-10-23 · UI 개선 · 침해 복구 현황 화면

- 공지문 형식의 봉쇄 안내를 보안관제센터가 침해를 복구하는 실시간 현황 화면으로 재구성했다. 경보 티커, 복구율과 4단계 진행(확산 차단 → 오염 정화 → 기록 복원 → 최종 검증), 재개 카운트다운, ERP 메뉴별 구역 복구 매트릭스, 실시간 대응 로그, 대응 경과 공지와 요원 행동 지침을 보여 준다.
- 복구 상태는 `lib/maintenance/recovery.ts`가 점검 시작 후 경과 시간만으로 계산한다. 같은 시각에 접속한 요원은 같은 화면을 보고 열어 둔 화면도 매초 갱신된다. 복구가 진행될수록 적색 손상 연출이 옅어지고 문장이 금색으로 돌아온다. 공지 문구와 게시 시각은 `RECOVERY_UPDATES`에서 관리한다.
- 첫 시안의 침입자 메시지와 화면 탈취 플래시는 사용자 요청으로 제거하고 실제 관제 대응 문구만 남겼다. 로그 IP는 문서용 예약 대역만 쓴다.
- `/maintenance/preview?minutes=N`으로 시작 후 N분 시점을 볼 수 있다. 개발 전용이며 기본값은 5분이고 운영에서는 계속 404다.
- 카운트다운·상태 확인·자동 복귀 effect는 이전 커밋과 같고 차단 경로(proxy·layout·gate)는 바꾸지 않았다.
- 검증: `tsc --noEmit`, 변경 경로 ESLint, `pnpm build`, `node --test lib/maintenance/__tests__/*.test.mjs` 17건 통과. 변경 등급 L3(콜백 인자명 `token` 오탐)에 따라 strict·pragmatic 순차 리뷰와 validator를 거쳐 클래스 합성, 로고 선택자 누수, 대비, 낭독 공백을 고쳤다.
- 화면 검수: headless Chromium 320~1440px과 시작 후 5·180·600분 시점에서 가로 넘침·콘솔 오류·hydration 경고 0건. 열어 둔 화면의 공지 게시와 단계 전환, 움직임 줄이기 설정에서 애니메이션 정지를 확인했다.
- 잔여: 기존 lifecycle이 SSR 시각을 마운트 시점에 고정하므로 첫 상태 확인(최대 15초) 전까지 화면 시계가 hydration 지연만큼 늦을 수 있다. 실제 활성 `/maintenance`와 운영 404는 이번에 다시 실행하지 않았다.
- 운영 경계: 로컬 구현·검증만 수행했다. 차단 구현 `d08f9c69`를 포함해 아직 main에 반영·배포하지 않았다.
