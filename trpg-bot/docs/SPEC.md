# TRPG 캘린더 디스코드 봇 — 현재 구현 명세

> 최종 대조일: 2026-10-23. 기준은 `src/index.ts`에서 실제 등록하는 명령·컴포넌트·이벤트·스케줄러다.

## 1. 문서 범위

이 문서는 현재 실행되는 `trpg-bot` 기능을 설명한다. 과거 Discord RSVP 봇 코드는 2026-10-23에 삭제했다. 필요하면 삭제 커밋의 부모에서 복구한다. 삭제 커밋은 `git log --diff-filter=D --oneline -- trpg-bot/src/commands/session-create.ts`로 찾는다. 다만 `registra-bot`과 길드·컬렉션 소유권을 먼저 다시 검토해야 한다.

초기 RSVP 설계와 후보 기능은 [`../trpg-discord-bot-plan.md`](../trpg-discord-bot-plan.md)에 역사적 자료로 남긴다.

## 2. 현재 역할

`trpg-bot`은 세션을 직접 생성하거나 참가 응답을 수집하지 않는다. 세션과 참가자는 `trpg-web`에서 관리한다. 봇의 책임은 다음과 같다.

1. `/세션확인`, `/내세션`으로 세션 일정 조회, `/일정투표`로 후보 날짜 투표
2. `/roll`, `/r`로 TRPG 주사위와 목표치 판정, `/비밀굴림`으로 지정한 사람에게만 결과 전달
3. `/도움말`로 활성 명령 사용법 제공
4. 세션 생성·수정·취소 알림과 시작 24시간·1시간 전 리마인드
5. 운영 Discord 길드의 멤버 정보를 DB에 동기화
6. YouTube 오디오를 음성 채널에서 재생
7. 운영 장애 알림, 음악 자동 점검, 생존 신호, `/상태` 진단

```text
trpg-web ── 세션 생성·수정·취소 ──> trpg_sessions
                                          │
                       ┌──────────────────┴──────────────────┐
                       │                                     │
                trpg-bot 폴링                       /세션확인·/내세션 조회
                       │                                     │
          참가자 DM → 실패 시 폴백 채널            Discord 캘린더·목록 응답
```

## 3. 활성 슬래시 명령과 컴포넌트

모든 명령은 `contexts: [Guild]`로 등록해 DM에는 보이지 않는다. 런타임에서도 `TRPG_GUILD_ID` 외 길드의 실행을 막는다.

### 3-1. `/세션확인`

운영 길드의 월간 `open` 세션을 Discord 임베드, 캘린더 PNG, 웹 캘린더 링크로 보여준다.

| 옵션 | 타입 | 필수 | 동작 |
| --- | --- | --- | --- |
| `연도` | 정수 | 아니요 | 미입력 시 KST 현재 연도. 등록 범위는 2026~2100 |
| `월` | 정수 | 아니요 | 미입력 시 KST 현재 월. 범위는 1~12 |
| `모드` | 선택 | 아니요 | `상세 보기`가 기본값, `요약만 보기`는 세션별 상세 필드 생략 |
| `내세션` | 불리언 | 아니요 | `true`면 내가 참가하거나 진행하는 세션만 표시 |
| `비공개` | 불리언 | 아니요 | `true`면 에페메랄 응답, 기본은 채널 공개 |

동작 규칙:

- 선택한 연·월의 `status: "open"` 세션을 일시 순으로 조회하고, KST 오늘 날짜보다 이전인 세션은 뺀다. 오늘 세션은 시작 시각이 지났어도 표시한다.
- 월간 요약에는 표시 세션 수, 오늘 일정 수, 오늘 이후 일정 수, 참가 대상 누적 인원을 싣는다.
- 상세 모드는 세션의 일시·마스터·참가자 명단을 보여준다.
  - 최대 12건까지 싣되, embed 전체 6000자 예산 안에서만 채우고 나머지는 `더 보기`(외 N건)로 센다.
  - 참가자 멘션은 세션당 최대 16명까지 싣고 나머지는 인원수로 줄인다.
- 웹 버튼은 조회한 달로 연다: `${TRPG_WEB_BASE_URL}/calendar?date=…`. 이번 달이면 오늘 날짜, 다른 달이면 그 달 1일이다.
- 응답에는 두 가지 컴포넌트가 붙는다.
  - `◀ 이전 달`·`다음 달 ▶` 버튼: 누르면 공개 메시지는 그대로 두고, 누른 사람에게 그 달 캘린더를 비공개로 새로 보여준다(같은 모드·범위). 이번 달 화면에서는 이전 달 버튼이 비활성이다. 지난 달은 항상 비어 있기 때문이다.
  - 상세 모드의 세션 선택 메뉴(최대 25건): 고른 세션의 참가자 전체(1024자 한도, 넘으면 `외 N명`)와 `?sessionId=` 웹 링크를 누른 사람에게 비공개로 보여준다. 이미 취소된 세션이면 안내만 한다.
- 컴포넌트 customId 접두사는 `trpg:session-check:v1:`이다. 형식이 맞지 않거나 옛 버전 customId면 "더 이상 사용할 수 없는 버튼"으로 안내한다.

캘린더 PNG:

- Puppeteer로 7열 월간 달력을 렌더링한다. Discord에서 원본을 확대해 읽을 수 있도록 1920px 가로형으로 그린다.
- 현재 월을 조회하면 오늘 날짜를 강조한다.
- 날짜별 세션은 시작 시각 순으로 최대 3건을 표시하고, 초과분은 `+N more`로 줄인다. 제목은 칸 안에서 여러 줄로 표시한다(HTML 이스케이프, 페이지 JavaScript 비활성).
- 렌더는 프로세스 안에서 직렬화한다. 큐 대기를 포함해 30초가 지나면 호출부에는 타임아웃을 먼저 돌려준다. 다음 렌더는 실제 작업이 끝난 뒤에만 시작한다.
- 타임아웃이 나면 페이지를 닫고 브라우저도 버린다. 멈춘 Chromium이 닫기에 응답하지 않으면 약 2초 뒤 프로세스를 강제 종료한다. 진행 중인 작업을 바로 끝내 다음 렌더가 막히지 않게 하기 위해서다.
- 브라우저가 끊기면 참조를 버리고 기존 Chromium을 닫은 뒤 다시 띄운다. Puppeteer 자체 SIGINT·SIGTERM·SIGHUP 처리는 끄고, 종료는 봇 shutdown이 맡는다.
- `RESULT_CARD_IMAGE=0`, `false`, `off`이면 PNG를 생성하지 않는다. PNG가 꺼져 있거나 실패·타임아웃이어도 텍스트 임베드와 웹 링크로 응답한다.

### 3-2. `/내세션`

내가 참가하거나 마스터로 진행하는 KST 오늘 이후 `open` 세션을 일시 순으로 비공개 응답한다.

| 옵션 | 타입 | 필수 | 동작 |
| --- | --- | --- | --- |
| `개수` | 정수 | 아니요 | 1~10, 기본 5 |

- 세션별로 일시(`<t:…:F> · <t:…:R>`), 마스터(내가 진행하면 표시), 참가 인원을 싣는다.
- 세션마다 `?sessionId=` 웹 링크 버튼을 붙인다(한 줄 5개).
- 세션이 없으면 웹 캘린더 링크만 준다.
- 조회는 shared-db `findUpcomingTrpgSessionsForParticipant`로 한다. 읽기 전용이다.

### 3-3. `/일정투표`

후보 날짜 2~10개로 Discord 기본 투표(Poll)를 열고, 마감되면 가장 많은 표를 받은 날짜를 투표 메시지에 답장한다. 세션은 만들지 않는다.

| 옵션 | 타입 | 필수 | 동작 |
| --- | --- | --- | --- |
| `날짜1`, `날짜2` | 문자열 | 예 | `2026-11-08`, `11-08`, `11/8`, `11-08 20:00` 형식 |
| `날짜3`~`날짜10` | 문자열 | 아니요 | 추가 후보 |
| `시각` | 문자열 | 아니요 | `HH:mm`. 시각을 적지 않은 후보에 붙인다 |
| `제목` | 문자열 | 아니요 | 투표 질문. 기본 `다음 세션 날짜 투표` |
| `마감` | 정수 | 아니요 | 투표 기간(시간) 1~168, 기본 48 |
| `복수선택` | 불리언 | 아니요 | 기본 켜짐 |

- 연도를 생략한 날짜는 올해(KST)로 보고, 이미 지났으면 내년으로 본다.
- 존재하지 않는 날짜, 지난 날짜, 잘못된 시각은 비공개로 사유를 알린다. 같은 후보는 하나로 합치고 시간순으로 정렬한다.
- 답변은 `11/08(일) 20:00` 형식(55자 이내)이다.
- 권한:
  - 실행한 사람에게 그 채널의 `투표 만들기(Send Polls)` 권한이 있어야 한다. 서버가 막아 둔 채널에서 봇이 우회로가 되지 않게 하기 위해서다.
  - 봇에는 `투표 만들기`와 마감 답장용 `채널 보기`·`메시지 기록 보기`·`메시지 보내기`(스레드면 `스레드에서 메시지 보내기`)가 필요하다.
  - 어느 쪽이든 부족하면 투표를 열지 않고 비공개로 안내한다.
- 마감 5초 뒤 결과를 읽는다. 집계가 확정되지 않았으면 30초 간격으로 최대 3회 다시 읽는다. 결과 답장의 내용은 다음과 같다.
  - 최다 득표 날짜. 동률이면 가장 이른 날짜를 고르고 동률 수를 함께 적는다.
  - `?date=` 웹 캘린더 링크(미리보기 없이)
  - 표가 하나도 없으면 날짜를 정하지 못했다고만 알린다.
- 마감 처리 예약은 프로세스 메모리 타이머다. 마감 전에 봇이 재시작하면 결과 답장은 빠진다. Discord가 직접 올리는 투표 종료 안내는 그대로 남는다. 투표를 연 사람에게 보내는 응답에도 이 한계를 적는다.

### 3-4. `/roll`, `/r`

두 명령은 같은 주사위 엔진을 쓰며, `/r`은 `/roll`의 단축 이름이다.

| 옵션 | 타입 | 필수 | 동작 |
| --- | --- | --- | --- |
| `식` | 문자열 | 예 | 주사위 식. 최대 500자 |
| `비공개` | 불리언 | 아니요 | `true`면 에페메랄 응답 |

지원 문법:

- 기본 주사위: `XdY`, `d20`, `d%`, `dF`
- 산술: `+`, `-`, `*`, `/`, 괄호
- 여러 식: 세미콜론(`;`)으로 최대 4개 분리
- 반복: `6 4d6 k3`처럼 식 앞에 반복 횟수(2~20회)를 둔다. 범위 밖 횟수는 오류다. 공백 뒤가 연산자면(`5 + 1d20`) 반복이 아니라 앞에 쓴 보정치로 계산한다.
- 폭발: `e`, `ie`
- 선택: `k`(높은 값 유지), `kl`(낮은 값 유지), `d`(낮은 값 제거)
- 리롤: `r`, `ir`. `ir`이 100회 안에 조건을 만족하지 못하면 오류다. `dF`에는 리롤을 쓸 수 없다.
- 성공 개수: `t`(성공), `f`(실패), `b`(봇치)
- 목표치 판정(범용): 식 끝에 `>=`, `<=`, `>`, `<`, `=`(`==`)와 숫자를 붙인다. 예: `1d100+10 >= 65`. 결과에 `✅ 성공`·`❌ 실패`를 표시하고, 반복 굴림은 `성공 N/M` 요약을 붙인다. 시스템 고유 규칙(CoC 성공 단계 등)은 두지 않는다.
- 플래그: `s`(간단히), `nr`(개별 결과 숨김), `p`(비공개), `ul`(입력 순서 유지)
- 주석: `!` 뒤의 텍스트
- 별칭: `+d20`, `-d20`, `+d%`, `-d%`, `attack`, `skill`, `save`, `dndstats`, `sr6`, `age`
- `식:help`를 입력하면 간단한 도움말을 에페메랄로 표시한다.

검증과 표시:

- 숫자·면·닫는 괄호 다음 공백 뒤에 숫자·여는 괄호가 오면(`1d20 5`, `2d6 1d4`) 연산자 누락으로 거부한다. 공백 뒤 옵션 문자(`4d6 k3`, `2d20 d1`)는 허용한다.
- 계산 과정은 실제 식 모양 그대로 보여준다. 예: `1d20 [6] - 1d4 [4]`, `1d20 [13] + 5`. 주사위 항 하나뿐이면 결과 목록만 보여준다.
- 한 주사위 항은 최대 100개, 면 수는 최대 1000이다. 한 요청이 만드는 개별 결과는 최대 1000개다.
- 식의 숫자나 계산 결과가 안전 정수 범위(±2^53−1)를 넘으면 `숫자가 너무 큽니다` 오류로 거부한다. `Infinity` 같은 값을 공개 게시하지 않기 위해서다.
- 메시지는 1900자 예산 안에서 만든다.
  - 넘치면 개별 결과부터 생략(간단 표시)하고, 그래도 넘치는 Roll은 `외 N개 생략`으로 센다.
  - 합계와 판정은 항상 남긴다. 여러 결과 중 최대 12개 Roll을 표시한다.
- 주석의 마크다운·마스킹 링크(`[글](주소)`)·멘션 문법은 이스케이프한다. 응답은 링크 미리보기를 끄고(SuppressEmbeds), 멘션 파싱을 비활성화한다.

### 3-5. `/비밀굴림`

`/roll`과 같은 문법으로 굴린 결과를 지정한 대상(보통 마스터)에게만 DM으로 보낸다.

| 옵션 | 타입 | 필수 | 동작 |
| --- | --- | --- | --- |
| `식` | 문자열 | 예 | 주사위 식 |
| `대상` | 사용자 | 예 | 결과를 받을 서버 멤버 |
| `나도보기` | 불리언 | 아니요 | 굴린 사람에게도 결과를 비공개로 보여줌 |

- 봇, 자기 자신, 서버 멤버가 아닌 사용자에게는 보낼 수 없다.
- 받은 DM 머리말에 굴린 사람과 서버 이름을 밝힌다.
  - 굴린 사람은 멘션(`<@id>`, 알림 핑 없음)과 서버 표시명(이스케이프)으로 함께 적는다. 닉네임만 바꿔 발신자를 위장할 수 없게 하기 위해서다.
  - DM은 머리말을 포함해 2000자 안에서 만든다. 굴림 본문 예산을 머리말 길이만큼 줄인다.
- 전달에 실패해도 공개 폴백 채널로 보내지 않는다. 굴린 사람에게는 사유와 "결과는 아무에게도 공개되지 않았다"는 사실만 알린다.
  - DM 거부(`50007`): 대상이 DM을 받지 않도록 설정했다고 안내한다.
  - 그 밖의 오류: 일시 오류로 전달하지 못했다고 안내하고 로그를 남긴다.
- 같은 사람은 10초에 한 번 보낼 수 있다(프로세스 메모리 쿨다운).

### 3-6. `/도움말`

현재 활성 명령의 사용 조건, 옵션, 실행 예시를 비공개 임베드로 제공한다.

| 옵션 | 타입 | 필수 | 동작 |
| --- | --- | --- | --- |
| `기능` | 선택 | 아니요 | `전체 명령`, `세션 확인`, `주사위`, `YouTube 음악`. 미입력 시 전체 |

- 전체 화면은 세션(`/세션확인`·`/내세션`·`/일정투표`), 주사위(`/roll`·`/r`·`/비밀굴림`), 음악, 운영(`/상태`)을 요약한다.

### 3-7. `/상태`

운영자용 진단이다. `default_member_permissions`를 서버 관리(Manage Guild)로 등록해 일반 사용자의 명령 목록에는 보이지 않고, 런타임에서도 권한을 다시 확인한다. 응답은 비공개다.

- 프로세스: 가동 시간, 메모리(RSS), 게이트웨이 ping, DB ping(3초 제한)
- 주기 작업의 마지막 실행 결과: 생성·수정·취소·24h·1h 알림, 멤버 동기화, 음악 자동 점검, 생존 신호
  - 성공 시각과 처리 건수를 싣고, 실패면 연속 횟수와 민감값을 제거한 원인을 싣는다.
- 음악: yt-dlp·FFmpeg 버전과 연결 수. 준비되지 않았으면 원인을 싣는다.
- 알림 설정: 1h 리마인드, 운영 알림 경로, 외부 생존 신호 사용 여부
- 기록은 메모리에만 있어 재시작 직후에는 "이력 없음"으로 표시한다.

입력·권한 규칙:

- `/음악 재생`은 YouTube·YouTube Music·`youtu.be` URL 또는 최대 200자의 검색어를 받는다. 다른 URL과 로컬 파일 스킴은 거부한다. 검색어는 yt-dlp `ytsearch1`로 첫 결과 한 건만 고른다.
- 모든 음악 명령과 상태판 버튼은 `TRPG_MUSIC_CHANNEL_ID`로 지정한 운영 길드의 일반 텍스트 채널에서만 동작한다.
- 일반 음성 채널만 지원하고 Stage 채널은 지원하지 않는다.
- 제어는 봇과 같은 음성 채널의 사용자만 할 수 있다.
  - 봇의 `Connect`·`Speak` 권한은 새로 연결하는 재생 요청에서만 확인한다.
  - 재생 중에 권한이 바뀌어도 일시정지·건너뛰기·퇴장으로 봇을 멈추거나 내보낼 수 있다.
- 관리자가 봇을 다른 음성 채널로 옮기면 세션이 새 채널을 따라간다. 제어 권한·자동 퇴장·상태판 모두 옮겨 간 채널 기준이다.
- 길드별 대기열은 메모리에 최대 100곡까지 유지하며 재시작 시 초기화한다.
- 길드별 yt-dlp 메타데이터 해석은 동시에 최대 2건만 실행한다. 해석 중인 요청은 대기열 슬롯과 음성 채널을 예약하며, 성공·실패·취소와 관계없이 `finally`에서 해제한다.

오디오 품질 경로:

1. yt-dlp는 `WebM + Opus` 최상 음원을 우선 선택한다. 미디어 URL과 요청 헤더는 실제 재생 직전에 다시 해석한다.
2. HTTP(S) WebM/Opus 소스는 `StreamType.WebmOpus` demux만 거치며 디코딩·재인코딩하지 않는다.
3. AAC·HLS·라이브처럼 직접 전달할 수 없는 소스만 FFmpeg/libopus로 한 번 변환한다(48 kHz stereo, 128 kbps VBR, 20 ms frame).
4. 음량이 기본값(100%)이면 볼륨·필터를 쓰지 않는다. 100%가 아니면 그 세션은 FFmpeg `volume` 필터를 거치는 변환 경로를 쓴다.
5. 재생 중 음량을 바꾸면 현재 곡을 재생 위치(`-ss`)부터 다시 연다(라이브는 처음부터). 일시정지 중에 바꾸면 다시 연 곡도 일시정지 상태로 이어진다. 음량 설정은 세션 메모리에만 남는다.
6. Discord 음성 연결은 `@discordjs/voice`의 기본 DAVE E2EE를 쓴다.
7. 미디어 URL 해석은 기본 player client `visionos`를 쓰고 `YT_DLP_PLAYER_CLIENTS`로 바꿀 수 있다. Docker 이미지는 bgutil POT provider를 같은 컨테이너에서 띄운다. provider가 죽으면 5초 뒤 다시 띄운다.
8. googlevideo가 미디어 URL을 HTTP 403으로 거부하면 폴백 프로필로 한 번 바꿔 다시 해석한다. 폴백 프로필은 `web_safari` + PO token, HLS·m4a 허용이다. 403이 아닌 실패는 서명 URL 만료로 보고 같은 프로필로 한 번만 재해석한다. 준비 시도는 총 3회로 제한한다.
9. 미디어 응답 헤더와 첫 오디오 데이터는 각각 20초 안에 도착해야 한다. 준비 중 `건너뛰기`·`초기화`·`퇴장` 또는 연결 종료가 일어나면, 같은 `AbortSignal`로 yt-dlp·HTTP·FFmpeg 작업을 취소한다.

채널 메시지와 상태판:

- 슬래시 명령의 성공·오류 응답은 모두 실행 사용자에게만 보이는 비공개 메시지다.
- 전용 채널에는 공개 상태판 임베드 한 개만 유지한다. 재생 준비·재생 중·일시정지·대기열·최근 오류·종료 사유를 같은 메시지 수정으로 반영한다.
- 연결된 상태판에는 버튼 네 개를 붙인다. 유휴 상태판에는 버튼이 없다.
  - ⏯ 일시정지·재개 토글, ⏭ 건너뛰기: 현재 곡이 있을 때만 활성
  - 🔁 반복: 끔 → 현재 곡 → 대기열 → 끔 순환
  - 🔀 셔플: 예약곡 2곡 이상일 때만 활성
  - 초기화·퇴장은 오클릭 위험 때문에 슬래시 명령으로만 제공한다.
  - 버튼은 슬래시 제어와 같은 규칙을 따른다. 성공하면 응답 없이 상태판 갱신으로, 실패하면 누른 사람에게만 비공개로 알린다.
- 상태판은 footer 표식으로 식별한다. 기동 시 최근 25개 메시지에서 봇이 작성한 상태판을 복구하고, 찾지 못했을 때만 새로 만든다.
- 상태판 수정은 한 번에 하나만 실행하고, 편집 중 들어온 화면은 가장 최신 스냅샷 하나로 합친다.
- 상태판 편집이 실패한 경우:
  - 일시적 실패(5xx·네트워크)면 같은 화면을 5·15·30초 백오프로 최대 3회 다시 보낸다.
  - 권한 오류(50001·50013)와 설정 오류는 다시 시도하지 않고 다음 상태 변화까지 기다린다.

자동 점검:

- 기동 1분 뒤 첫 점검을 하고, 이후에는 각 점검이 끝난 뒤 다음 점검을 예약한다. 겹쳐 실행하지 않는다.
  - 정상이면 24시간 뒤, 결과가 나쁘면 1시간 뒤(기본 주기보다 길지 않게) 다시 점검한다.
- 점검은 해석 프로필별로 실제 재생과 같은 연속 Range 경로로 최대 8 MiB까지 받는다. 음성 채널에는 연결하지 않는다.
- 판정은 `healthy`(기본 프로필 정상) / `degraded`(폴백만 정상) / `down`(전부 실패)이다. 프로필마다 최대 2회 시도하고, 시도마다 45초 제한이 있다. 시간 초과면 원인을 `점검 시간 45초 초과`로 남긴다.
- 알림 규칙:
  - `degraded`는 warning, `down`은 critical로 보낸다. 프로필별 실패 단계·HTTP 상태, yt-dlp 버전, POT provider 응답 여부(`/ping`), 다음 점검 시각을 함께 싣는다.
  - 정상으로 돌아오면 복구를 info로 한 번 알린다.
  - 기동 뒤 첫 점검이 정상이어도 info로 한 번 알린다. 재배포로 고친 뒤 "고쳐졌음"과 "점검이 안 돌았음"을 구분하기 위해서다.
- 봇을 종료하면 진행 중인 점검 요청도 취소한다.

운영 장애 알림(음악):

- 단일 재생 소스 실패는 공개 상태판에만 반영한다.
- 최근 1시간 안에 재생 실패가 3회 이상이면 운영자에게 알린다. 중간에 복구된 곡도 포함하고, 성공해도 횟수를 초기화하지 않는다. 알림에는 yt-dlp 버전·player client·POT provider 응답 여부를 싣는다.

수명주기:

- 연결이 끊기면 최대 5회 점증 지연 재연결을 시도한다. 서버가 이동·퇴장시킨 연결은 5초 동안 재연결 신호를 기다린 뒤 정리한다.
- 음성 채널에 일반 사용자가 없으면 30초 뒤, 대기열이 빈 채 5분이 지나면 자동으로 나간다.
- 음악 런타임 준비 실패 처리:
  - 실패해도 세션 조회·알림·멤버 동기화는 계속 실행한다.
  - 일시적 실패(REST 5xx, yt-dlp 콜드스타트 지연 등)면 마지막 시도에서 1분이 지난 뒤의 음악 요청에서 다시 준비한다. 준비에 성공한 첫 순간 자동 점검을 시작한다.
  - 전용 채널 미설정·오설정은 재시작 전까지 다시 시도하지 않는다.

## 4. 자동 알림

### 4-1. 공통 발송 흐름

생성·수정·취소 알림은 `TRPG_POLLING_INTERVAL_MS` 주기(기본 60초, 허용 10초~10분)로 확인한다. 리마인드는 `TRPG_REMINDER_INTERVAL_MS` 주기(기본 300초, 허용 30초~15분)로 확인한다. 모든 스케줄러는 봇 기동 직후 한 번 실행된다. 네 종류(+1h 리마인드)는 공용 팩토리 `scheduler/notification-scheduler.ts`의 설정만 다르다.

처리 순서:

1. DB에서 미발송 후보 세션을 조회한다.
2. 5분 lease로 발송권을 원자적으로 선점한다. 선점 필터에는 조회 시점의 회차 스냅샷을 넣는다(수정은 `updateNotificationQueuedAt`, 리마인드는 `date`·`startTime`).
3. 선점 뒤 세션을 다시 조회해 최신 문서로 메시지와 수신자를 만든다. 회차가 바뀌었으면 lease만 풀고 다음 tick으로 넘긴다.
4. 수신자별로 같은 회차에 이미 전달된 기록이 있으면 건너뛰고, 없으면 DM을 시도한다(실패 처리는 §4-7).
5. `trpg_session_notifications`에 `dm`·`fallback`·`failed` 결과와 회차 키를 기록한다.
6. 수신자를 다 돌면 그 회차를 완료로 표시한다. 완료 표시 필터에도 회차 스냅샷을 넣는다. 발송 중 재수정·재일정으로 회차가 바뀌었으면 완료 대신 lease만 풀어, 다음 tick이 최신 회차를 바로 처리한다.

각 스케줄러는 이전 tick이 끝나지 않았으면 다음 tick을 건너뛴다. lease는 여러 워커·재시작 상황에서 같은 세션의 동시 처리를 막는다.

- 선점한 뒤 세션 처리 중 예외가 나면 lease를 바로 풀어 다음 tick이 다시 처리하게 한다. 그 tick의 실행 기록은 실패로 남기고 운영 알림(`trpg-scheduler:<종류>:session-error`, warning)을 보낸다.
- 수정 알림은 생성 알림이 끝난 뒤(`notificationSentAt` 기록 후)에만 선점한다. 생성 발송이 중단됐다가 재기동되더라도 수정 DM이 생성 DM보다 먼저 도착하지 않게 하기 위해서다.
- 취소 알림은 생성 알림이 발송 중(생성 lease 활성)일 때만 기다린다. 취소된 세션은 생성 알림이 재개되지 않으므로 완료를 기다리지 않는다.
- 종료가 시작되면 새 tick은 DB를 조회하지 않고 바로 끝난다.

알림 임베드에는 세션 제목, `YYYY-MM-DD HH:mm (KST)`와 Discord 절대·상대 시각, 마스터 이름, 현재 참가자 수와 멘션 명단, 웹 캘린더 버튼이 들어간다.

수신자 규칙(사용자 결정 2026-10-22):

- 생성·수정·취소 알림은 GM(`createdByDiscordId`) 본인에게 보내지 않는다. 웹에서 직접 한 행동이기 때문이다. 제외한 뒤 수신자가 없으면 DM 없이 완료 처리한다.
- 24시간·1시간 전 리마인드는 GM에게도 보낸다.
- 세션 시작 시각이 이미 지났으면 생성·수정·취소 알림은 DM 없이 완료 처리한다(긴 다운타임 뒤 지난 세션 안내 방지).

### 4-2. 생성 알림

- 대상: 생성 알림이 완료되지 않은 `open` 세션
- 수신자: `participantDiscordIds`에서 GM을 뺀 사람
- 버튼: 세션 ID를 포함한 웹 캘린더 URL
- 사용자별 기존 성공 기록이 있으면 다시 보내지 않는다.

### 4-3. 수정 알림

- 대상: 수정 알림 대기열에 들어간 `open` 세션
- 수신자: `updateNotificationRecipientDiscordIds` 스냅샷에서 GM을 뺀 사람. 스냅샷은 첫 대기 시점 참가자(baseline)와 최신 참가자의 합집합이므로, 제외된 참가자도 변경 사실을 받는다.
- 변경 요약(`updateNotificationChanges`)은 임베드에 표시한다.
- 연속 수정: 완료되지 않은 수정 회차가 있을 때 다시 수정하면, 첫 대기 시점의 `updateNotificationBaseline`을 그대로 두고 최신 상태와 다시 비교해 누적 요약을 만든다. 발송 중(lease 활성)이어도 같다.
  - 이때 회차 키(`updateNotificationQueuedAt`)를 새로 발급한다. 발송 중이던 회차는 완료 표시가 거부되어 lease만 풀리고, 다음 tick이 누적 요약을 수신자 전원에게 다시 보낸다. 이미 일부 요약을 받은 사람은 같은 내용을 한 번 더 받을 수 있다.
  - 처음 상태로 되돌리면: 발송 중이 아니면 대기를 해제한다. 발송 중이면 현재 문서 기준 정정 회차를 만든다.
  - 현재 문서와 같은 값으로 다시 저장하면(바뀐 것 없음) 대기 회차를 그대로 둔다. 회차 키를 새로 발급하지 않으므로 같은 DM이 다시 나가지 않는다.
- 회차 키 `updateNotificationQueuedAt`으로 사용자별 중복 발송을 막는다(크래시·배포 겹침 후 재처리).
- 생성 알림 발송이 한 번도 시작되지 않았으면(선점 기록 `notificationClaimedAt` 없음) 수정 대기열을 쌓지 않는다. 생성 알림이 최신 내용으로 나가기 때문이다. 생성 알림이 일부만 나간 채 중단됐다면 이미 받은 사람이 있으므로 수정 알림을 쌓는다. 이 판정은 갱신 필터 조건으로 원자적으로 하고, 경합하면 다시 판단한다(최대 5회).
- 재일정(날짜·시각이 실제로 바뀔 때만)은 24h·1h 리마인드 발송 상태를 초기화한다.

### 4-4. 취소 알림

- 대상: 취소 알림 대기열에 들어간 `cancelled` 세션. 기능 배포 전부터 취소 상태였던 과거 세션은 대기열 시각이 없으므로 발송하지 않는다.
- 생성 알림 발송이 한 번도 시작되지 않은(아무도 안내받지 않은) 세션을 취소하면 취소 알림도 쌓지 않는다. 생성 알림이 일부라도 나갔으면(선점 기록 있음) 취소 알림을 쌓는다. 취소된 세션의 생성 알림은 재개되지 않으므로, 이미 받은 사람이 취소 사실을 놓치지 않게 하기 위해서다.
- 수신자: `participantDiscordIds`에서 GM을 뺀 사람
- 버튼: 취소된 날짜를 기준으로 웹 캘린더를 연다.

### 4-5. 시작 24시간 전 리마인드

- 대상: 이번 회차(`date`·`startTime`)의 24h 리마인드가 아직 나가지 않았고 생성 알림은 이미 나간 `open` 세션
- 수신자: 참가자와 GM
- 조회 창은 현재 시각 + 24시간 ± 2×주기(기본 ±10분)이다. 겹치는 창과 원자적 선점으로 누락과 중복을 줄인다.
- 회차 키 `${date} ${startTime}`로 중복을 판정한다. 재일정하면 새 시각의 리마인드가 기존 수신자 전원에게 다시 간다. 같은 회차 안에서는 사용자별로 한 번만 보낸다.
- 생성 알림이 30분 이내에 나갔으면 DM 없이 그 회차를 완료 처리한다(생성 직후 중복 안내 방지).
- 조회 창을 놓친 세션(긴 다운타임, 24시간 이내로 옮긴 재일정)은 따라잡아 보내지 않는다(사용자 결정). 재일정은 수정 알림이, 임박한 세션은 1시간 전 리마인드가 대신한다.

### 4-6. 시작 1시간 전 리마인드

- `TRPG_REMINDER_1H`가 `0`·`false`·`off`가 아니면 켜진다(기본 켜짐).
- 조회 창은 현재 시각 + 1시간 ± 2×리마인드 주기이고, 제목은 "곧 TRPG 세션이 시작됩니다"이다.
- 대상·수신자·회차 키·30분 규칙은 24h 리마인드와 같다(문서 필드 `reminder1hSentAt`·`reminder1hClaimLeaseUntil`, 로그 kind `reminder1h`).

### 4-7. 발송 실패 처리

- DM 실패 분기:
  - `50007`(이 사용자에게 보낼 수 없음): 바로 폴백 채널에 `<@userId>` 멘션과 같은 안내를 보낸다.
  - `10013`(Unknown User): 폴백 없이 `failed`로 기록한다.
  - 그 밖의 실패(다른 API 오류, 네트워크 오류·타임아웃): 봇이 다시 시도하지 않고 바로 폴백한다. 네트워크 오류·타임아웃은 Discord REST 계층(`@discordjs/rest`)이 이미 3회 재시도한 뒤의 결과다. 또 응답만 유실된 경우라면 다시 보낼 때 DM이 중복된다.
- 길드를 떠난 멤버(`trpg_guild_members.leftAt`가 있음)에게는 DM만 시도하고 공개 폴백 멘션은 하지 않는다. DM이 실패하면 `failed`와 `left guild`를 기록한다.
- 개별 사용자 오류는 기록하고 다음 참가자로 넘어간다. 수신자를 다 돌면 그 회차는 완료 처리된다. `failed` 수신자를 자동으로 다시 시도하는 큐는 없다.
- 세션 하나에서 `failed`가 1명 이상이면 운영 알림(`trpg-scheduler:<종류>:delivery-failed`, warning)을 보낸다. 내용은 세션·제목·실패 수·첫 오류다.
  - 길드를 떠난 멤버와 삭제된 계정(`10013`)의 실패는 예상된 실패라 기록만 하고 알림 대상에서 뺀다.
  - key가 스케줄러 단위라 같은 종류의 알림은 기본 10분에 한 번만 간다.
- tick 자체가 실패하면(DB 장애 등) 운영 알림(`trpg-scheduler:<종류>:tick`, critical, 1시간 중복 억제)을 보낸다.
- 종료 신호를 받으면 진행 중인 발송은 다음 수신자로 넘어가지 않고 멈춘다. 완료 표시 없이 lease만 풀어, 다음 인스턴스가 남은 수신자만 이어서 처리한다. 그 사이 수정이 들어오면 새 회차로 전원에게 다시 보낸다(§4-3).

## 5. 길드 멤버 동기화

동기화 대상은 `TRPG_GUILD_ID` 운영 길드의 일반 사용자이며 봇 계정은 제외한다.

| 시점 | 처리 |
| --- | --- |
| 봇 준비 완료 | 길드 전체 멤버 fetch 후 DB와 reconcile |
| `GuildMemberAdd` | 신규 멤버 upsert |
| `GuildMemberUpdate` | username·표시명 등 upsert |
| `GuildMemberRemove` | `leftAt` 기록 |
| 24시간마다 | 누락 이벤트 보정을 위한 전체 재동기화 (실패 시 운영 알림 `member-daily-sync`) |

- 표시명은 서버 nickname → Discord global name → username 순으로 정한다.
- 전체 동기화는 Discord에 없는 DB 활성 멤버에게 `leftAt`을 기록한다. 단, 동기화를 시작한 뒤 이벤트로 갱신된 멤버(`lastSyncedAt`이 시작 시각 이후)는 건드리지 않는다.
- 반대 방향은 막지 않는다. 동기화 도중(멤버 목록을 받은 뒤 DB 반영이 끝나기 전) 나간 멤버는 동기화 갱신이 `leftAt`을 지울 수 있다(§10).
- 결과는 `/상태`에 `멤버 동기화`로 보인다.

## 6. 데이터 저장

봇은 `@stargate/shared-db`를 통해 MongoDB에 장기 실행 모드로 연결한다. 기본 DB 이름은 `stargate`다. **인덱스는 봇이 만들지 않는다.** 배포 전 운영자가 shared-db preflight로 만든다.

### 6-1. `trpg_sessions`

| 필드 | 설명 |
| --- | --- |
| `guildId` | 세션 소유 길드 |
| `title` | 세션 제목 |
| `date`, `startTime` | KST 진행 날짜와 시각 |
| `createdByDiscordId`, `createdByUsername` | 마스터 정보 |
| `participantDiscordIds` | 알림 대상 참가자 |
| `status` | `open` 또는 `cancelled` |
| `*NotificationQueuedAt` | 수정·취소 알림 대기열 시각(수정 알림의 회차 키) |
| `updateNotificationBaseline` | 수정 알림 첫 대기 시점의 제목·일시·참가자(연속 수정 병합 기준) |
| `*NotificationSentAt`, `reminderSentAt`, `reminder1hSentAt` | 알림 완료 시각 |
| `*ClaimLeaseUntil` | 발송권 lease 만료 시각 |
| `notificationClaimedAt` | 생성 알림 발송권을 마지막으로 선점한 시각. lease를 풀어도 지우지 않고, 값이 있는지만 판정에 쓴다(생성 알림이 일부라도 나갔는지) |

새 필드(`updateNotificationBaseline`, `notificationClaimedAt`, `reminder1h*`)가 없는 기존 문서도 그대로 동작한다. baseline 없이 대기 중인 기존 수정 알림은 그대로 발송된다. 발송 전에 다시 수정되면 그 시점 문서를 baseline으로 새 요약을 만든다. 1h 리마인드 후보 조회용 인덱스 `trpg_sessions_reminder1h_pending`(`{ status, reminder1hSentAt, date, startTime }`)은 정의만 있으므로 운영자가 preflight로 만든다. 세션 수가 적어 인덱스가 없어도 동작은 한다.

### 6-2. `trpg_guild_members`

- Discord 사용자 ID, username, 표시명, 가입 시각
- 마지막 동기화 시각
- 탈퇴 시각 `leftAt`; 활성 멤버는 `null`

### 6-3. `trpg_session_notifications`

- 세션 ID와 수신자 Discord ID
- 종류: `creation`, `update`, `cancellation`, `reminder24h`, `reminder1h`
- 방식: `dm`, `fallback`, `failed`
- 회차 키 `roundKey`: 리마인드는 `${date} ${startTime}`, 수정은 대기열 시각(ISO). 생성·취소는 없음
- 시도 시각과 오류 문자열

## 8. 커맨드 등록과 운영 경계

- `GUILD_ID`가 있으면 해당 길드에, 없으면 글로벌로 활성 명령 9개를 등록한다.
- 등록 범위를 전환해도 이전 범위의 커맨드는 자동 삭제되지 않는다.
- 모든 명령은 `contexts: [Guild]`이고, 명령이 글로벌로 노출되더라도 런타임에서 `TRPG_GUILD_ID` 외 길드 실행을 막는다.
- 봇은 단일 운영 길드를 전제로 한다.
- `/일정투표`에는 대상 채널의 `투표 만들기`·`채널 보기`·`메시지 기록 보기`·`메시지 보내기`(마감 답장용) 권한이, 음악에는 `연결`·`말하기`가 필요하다. 폴백 채널에는 `채널 보기`·`메시지 보내기`·`링크 임베드`가 필요하다.

## 9. 운영과 장애 대응

- 운영 장애 알림(`TRPG_ALERT_USER_ID` DM, 선택적으로 `TRPG_ALERT_CHANNEL_ID`):
  - 보내는 경우: 슬래시 커맨드 등록 실패, Discord 클라이언트 오류, 명령·컴포넌트 처리 예외(명령별 key), 처리되지 않은 비동기 오류, 처리되지 않은 예외, 폴백 채널 설정 오류, 알림 스케줄러 tick·세션 처리·발송 실패, 멤버 동기화 실패, 음악 런타임·상태판·음성 연결 실패, 반복 재생 실패, 자동 점검 결과
  - 같은 key는 기본 10분 동안 한 번만 보낸다(tick 실패는 1시간).
  - 알림에는 오류 스택이나 URL·토큰·인증값을 싣지 않는다.
  - 등급은 info(복구·정상 확인) / warning / critical이다.
- 처리되지 않은 Promise 거부는 알리고 계속 실행한다. 처리되지 않은 동기 예외는 알린 뒤(최대 2초 대기) 정리하고 종료 코드 1로 끝낸다. 컨테이너 재시작 정책이 다시 띄운다.
- 생존 신호: 60초마다 게이트웨이 shard가 모두 Ready이면 생존 신호 파일을 갱신한다.
  - 판정은 shard 상태로 한다. discord.js의 `client.ws.status`는 최초 Ready 뒤 재연결·단절을 반영하지 않기 때문이다.
  - DB ping(5초 제한)도 함께 확인하지만, 실패해도 파일은 갱신하고 `/상태`에만 남긴다. 재시작으로는 DB 장애를 고칠 수 없다. 또 부팅은 DB 연결에 실패하면 종료하므로 재기동 루프가 되어, DB가 필요 없는 음악·주사위까지 끊긴다. DB 장애는 알림 스케줄러의 tick 실패 알림(critical)으로 드러난다.
  - `TRPG_HEARTBEAT_URL`이 있으면 같은 시점에 GET push를 보낸다. push 실패는 봇 상태와 무관하고, URL은 로그에 남기지 않는다.
  - Docker `HEALTHCHECK`는 파일이 3분 넘게 갱신되지 않으면 unhealthy로 판정한다. 간격 60초, 기동 유예 120초, 3회 연속이다.
  - 실제 재시작 여부는 배포 방식(Dokploy 설정)에 따른다.
- 종료 절차(SIGINT·SIGTERM): 두 번째 신호는 무시하고, 단계별 상한을 두며, 9초 안에 반드시 끝낸다(Docker 기본 유예 10초). 순서는 다음과 같다.
  1. 인터벌 정리
  2. 진행 중 알림 tick 대기(최대 3초)
  3. 음악 정리(2초)
  4. Discord 클라이언트 종료(1.5초)
  5. 캘린더 브라우저(1초)
  6. MongoDB(1초)
- 배포 게이트: main 푸시는 GitHub Actions `test-trpg`가 통과해야 Dokploy 웹훅을 호출한다.
  - `test-trpg`는 shared-db 빌드와 알림 상태 전이 테스트(`test:trpg`), trpg-bot typecheck·test를 돌린다. Atlas에 접속하는 shared-db race 테스트는 돌리지 않는다.
  - 감지 경로는 다음뿐이고, 문서·테스트만 바꾼 푸시는 배포하지 않는다.
    - `trpg-bot/src/**`, `package.json`, `tsconfig.json`, `Dockerfile`, `docker-entrypoint.sh`
    - shared-db, 루트 `package.json`·lockfile·`.dockerignore`·`scripts/clean-package-dist.mjs`
  - Dokploy 앱의 Auto Deploy(GitHub 연동)는 꺼 두고 웹훅으로만 배포한다. 켜 두면 Dokploy가 푸시마다 직접 빌드해 이 게이트를 우회한다.

## 10. 현재 제한 사항

- Discord에서 세션을 생성·수정·취소하거나 참석·불참 응답을 받을 수 없다. `/일정투표`도 세션을 만들지 않는다.
- `/세션확인`·`/내세션`은 `open` 세션만, KST 오늘 이후만 보여준다. 오늘 이미 시작한 세션은 표시될 수 있다.
- 캘린더와 알림 시각은 KST 고정이며 사용자별 타임존 설정은 없다.
- PNG 렌더에는 Puppeteer가 실행할 Chromium 환경이 필요하다.
- 자동 알림의 개별 완전 실패는 기록되고 운영자에게 알려지지만(이탈 멤버·삭제 계정 제외) 자동 재시도되지 않는다.
- 놓친 24h 리마인드(긴 다운타임, 24시간 이내 재일정)는 따라잡지 않는다.
- 수정 알림을 일부에게 보낸 뒤 종료로 중단됐고, 재기동 전에 GM이 원래 상태로 되돌리면 대기가 해제된다. 이미 받은 사람은 되돌린 사실을 안내받지 못한다.
  - 같은 이유로, 일부에게 나간 변경을 이후 수정에서 원래 값으로 돌리면 그 항목은 누적 요약에서 빠진다.
  - 세 조건(발송 중 종료, 재기동 전 수정, 원래 값으로 복귀)이 겹쳐야 생기는 경우라 따로 처리하지 않는다. 일시는 24시간·1시간 전 리마인드가 실제 값으로 다시 알린다.
- 전체 멤버 동기화 도중 나간 멤버는 다음 24시간 동기화 전까지 활성으로 남을 수 있다. 그 사이 그 멤버의 DM이 실패하면 폴백 채널에 멘션이 갈 수 있다.
- 알림 후보 조회는 `TRPG_GUILD_ID`로 필터하지 않는다. `trpg_sessions`를 단일 운영 영역으로 쓴다는 전제다.
- 반복 일정, 참가 상한·대기열, 외부 캘린더 동기화는 지원하지 않는다.
- 다음 상태는 프로세스 메모리에만 있어 재시작하면 초기화된다.
  - 음악 대기열·볼륨·반복
  - `/일정투표` 마감 답장 예약
  - `/비밀굴림` 쿨다운
  - `/상태` 실행 기록
- 음악 EQ·영구 대기열·탐색(seek)은 지원하지 않는다.
- YouTube의 추출 정책·서명·호스팅 IP 제한이 바뀌면 일부 영상이 일시적으로 재생되지 않을 수 있다.
