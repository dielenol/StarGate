# CENSOR-3 제작 동의 투표

Registra가 `ZULU-0028 파쇄음절탄 「CENSOR-3」` 3발의 제작 동의 표를 수집하는 로컬 구현 규격이다.

## 운영 흐름

1. 서버 관리 권한자가 `/제작투표 생성`을 실행한다.
2. `요청참조`, `응답마감(YYYY-MM-DD HH:mm)`, 실제 관료 `투표역할`을 모두 명시한다.
3. Registra는 지정 채널 `1534753076399833249`에 동의/반대 버튼을 게시한다.
4. 지정 역할 보유자는 마감 전까지 응답할 수 있으며, 재클릭은 본인의 이전 응답을 덮어쓴다.
5. 마감 후 서버 관리 권한자가 `/제작투표 결론`에서 `승인`, `반려`, `보류` 중 하나와 사유를 직접 기록한다.
6. Registra는 후속 ERP 수동 검토용 JSON receipt를 발급한다.

`/제작투표 현황`은 투표 ID 기준 현재 집계와 상태를 비밀 열람한다.
동일 길드의 동일 `요청참조`는 Mongo `_id` 단일성으로 한 번만 생성된다. 재투표가 필요하면 ERP에서 별도 요청 참조를 발급해야 한다.
결론이 기록된 투표의 `/제작투표 현황`은 JSON receipt를 다시 발급하므로, 최초 결론 응답 전달 실패 뒤에도 복구할 수 있다.

## Discord 게시 복구

원장은 `PENDING → DISPATCHING → SENT` 전달 상태를 보존한다. `DISPATCHING` 중 프로세스가 중단되면 중복 공지를 피하기 위해 자동 재전송하지 않는다.

서버 관리자는 채널을 직접 확인한 뒤 `/제작투표 게시복구`에서 다음 중 하나를 명시한다.

- 공지가 없음을 확인했다면 `미게시 확인·재시도 허용`을 선택한다. 원장은 `PENDING`으로 돌아가며 동일 요청참조의 생성 명령으로 재게시할 수 있다.
- 공지가 존재한다면 `기존 공지 연결`과 해당 Discord 메시지 ID를 선택한다. Registra가 작성했고 같은 투표 ID의 동의·반대 버튼을 모두 가진 메시지만 연결한다.

`SENT` 원장인데 연결된 공지가 삭제됐거나 조회되지 않는 경우에도 자동으로 정상 처리하지 않는다. 결론 기록을 차단하며, 관리자가 채널을 확인한 뒤 위 복구 절차로 `PENDING` 전환 또는 기존 공지 재연결을 명시해야 한다.

복구 동작, 관리자 Discord ID, 사유, 시각은 원장의 `publication.reconciliations`에 남는다.
동시 응답 화면은 원장의 단조 증가 `revision`을 Discord 편집 뒤 재확인해 오래된 집계가 마지막에 남지 않도록 보정한다.

## Fail-closed 경계

- 투표 기간은 생성 호출자가 직접 입력한다.
- 투표권 역할은 생성 호출자가 직접 선택한다. 코드에서 관료 역할 ID를 추정하지 않는다.
- 통과 기준, 정족수, 동률, 무투표 규칙은 자동 판정하지 않는다.
- 응답 마감 전에는 GM 결론을 기록할 수 없다.
- 결과 receipt는 ERP 승인 근거일 뿐이다. 크레딧 차감, 재료 소모, 공방 상태 변경, 장비·탄환 지급을 실행하지 않는다.
- JSON receipt 단독 파일은 권위 있는 원장이 아니다. 후속 consumer는 `verification.lookup`의 `voteId + guildId`로 `registrar_crafting_votes`를 재조회하고 명시된 필드를 대조해야 한다.
- 라이브 Discord 메시지와 투표 원장은 실제 명령 실행 시에만 생성된다. 이 구현 작업에서는 메시지 전송이나 라이브 DB mutation을 수행하지 않았다.
